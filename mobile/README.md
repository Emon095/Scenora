# SCENORA Android

SCENORA Android is the native Flutter/Dart client for **SCENORA — A Social Movie & Series Review Platform**. This application lives in the `mobile/` directory and is developed on the `android-flutter` branch. The existing Next.js web application remains available on `main`.

> **Mobile development boundary:** Work inside `mobile/` for the Android application. Do not replace the root Next.js project, its `src/` directory, or its web-oriented `package.json`.

## Application scope

The current mobile MVP follows the supplied SCENORA design references and provides the core social movie experience:

| Area | Current behavior |
|---|---|
| Home | Reviewer ranking, feed filters, social review cards, likes, and trending movie rail |
| Explore | Movie search, genre grid, trending titles, and top review preview |
| Create | Select a title, choose a 1–5 star rating, write a review, add image/tag actions, and save a draft confirmation |
| Movie Details | Hero artwork, metadata, community rating, synopsis, director/language information, save action, trailer action, and related titles |
| Shoutbox | Local live-chat presentation with text, image, voice-style messages, reactions, typing status, and message composition |
| Profile | Reviewer identity, statistics, saved movie area, recent reviews, and settings entry point |
| Secondary screens | Notifications, privacy/settings placeholders, appearance, language, and sign-out controls |

The application starts in **demo mode** so a reviewer can launch it without credentials. The data and service boundaries are ready for the existing Supabase schema and TMDB Edge Function to be connected incrementally.

## Development prerequisites

Install the [Flutter SDK](https://docs.flutter.dev/get-started/install) on the stable channel. The project currently targets Dart 3.13 or later. Install Android Studio or the Android command-line tools, an Android SDK platform, Android build tools, an Android emulator or a physical device, and a full JDK rather than a Java runtime-only installation.

After installing the tools, verify the environment from the `mobile/` directory:

```bash
flutter --version
flutter doctor -v
flutter devices
```

Accept the Android SDK licenses when requested:

```bash
flutter doctor --android-licenses
```

The local `android/local.properties` file is machine-specific and must not be committed. Flutter or Android Studio will create it for the local SDK path.

## Run the application

Clone the repository, switch to the Android branch, and run the project from `mobile/`:

```bash
git clone https://github.com/hakimshifat/Scenora.git
cd Scenora
git checkout android-flutter
cd mobile
flutter pub get
flutter run
```

To select a device explicitly:

```bash
flutter devices
flutter run -d <device-id>
```

The current UI uses remote poster, backdrop, and avatar URLs during normal development. The widget test switches `loadRemoteImages` off and uses `assets/images/placeholder.png`, which keeps automated tests deterministic without disabling remote images in the app.

## Backend configuration direction

The client is deliberately usable without a backend. `ScenoraConfig.fromEnvironment()` recognizes these optional compile-time values:

```text
SCENORA_SUPABASE_URL
SCENORA_SUPABASE_PUBLISHABLE_KEY
SCENORA_TMDB_FUNCTION_URL
```

A future remote build can receive them through `--dart-define`:

```bash
flutter run \
  --dart-define=SCENORA_SUPABASE_URL=https://your-project.supabase.co \
  --dart-define=SCENORA_SUPABASE_PUBLISHABLE_KEY=your-publishable-key \
  --dart-define=SCENORA_TMDB_FUNCTION_URL=https://your-project.supabase.co/functions/v1/tmdb-sync
```

The Android app must never contain a TMDB secret or Supabase service-role key. TMDB requests should go through the existing Supabase `tmdb-sync` Edge Function. The relevant database contracts already exist in [`../database/scenora.sql`](../database/scenora.sql), including profiles, posts, reviews, likes, comments, follows, saved movies, notifications, Shoutbox messages, reactions, and media storage policies.

## Quality checks

Run the following commands before pushing mobile changes:

```bash
cd mobile
dart format lib test
flutter analyze
flutter test
flutter build apk --debug
```

The debug APK is generated at:

```text
mobile/build/app/outputs/flutter-apk/app-debug.apk
```

For a release build, configure signing credentials outside the repository and use Flutter's standard release process:

```bash
flutter build apk --release
```

Do not commit signing keys, keystores, passwords, `.env` files, `android/local.properties`, or service credentials.

## Common Android issues

| Symptom | Resolution |
|---|---|
| `No Android SDK found` | Set up Android Studio or the command-line SDK, then run `flutter doctor -v`. |
| Gradle cannot find `JAVA_COMPILER` | Install a full JDK and set `JAVA_HOME` to the JDK directory; a JRE alone is insufficient. |
| No device is listed | Start an emulator or enable USB debugging on a physical Android device, then run `flutter devices`. |
| Images are blank offline | This is expected for demo network artwork; widget tests use the bundled placeholder asset. |
| Supabase/TMDB values are missing | Run in demo mode or provide the optional `--dart-define` values described above. |

## Branch and commit workflow

All Android work belongs on `android-flutter`. Keep the `main` branch focused on the existing web application. Before pushing, format and test the mobile project, review the diff, and commit with a focused message:

```bash
git checkout android-flutter
git pull --rebase origin android-flutter
cd mobile
dart format lib test
flutter analyze
flutter test
cd ..
git add mobile
git commit -m "Describe the Android change"
git push origin android-flutter
```

Use a pull request from `android-flutter` into `main` only after the mobile change has been reviewed and the web project remains unaffected.
